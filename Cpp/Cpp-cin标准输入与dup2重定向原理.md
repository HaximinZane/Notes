# C++ 标准输入、终端继承与 Shell 输入重定向原理

## 1. 核心结论

`cin` 读取的不是"键盘"，而是 C++ 的标准输入流。

在常见的 Linux 交互式终端中，Shell
自己的标准输入通常连接到当前终端。Shell
启动一个没有指定输入重定向的程序时，新程序通常继承 Shell
的标准输入，因此程序中的 `cin` 看起来就是从键盘读取。

执行：

``` bash
./a < t.txt
```

时，Shell 会在启动程序之前打开
`t.txt`，再通过文件描述符操作，把新程序的标准输入（文件描述符
0）改为指向这个文件。之后程序照常执行：

``` cpp
cin >> a >> b;
```

`cin`
不需要知道数据来自文件；它只从标准输入读取，而标准输入此时已经连接到文件。

------------------------------------------------------------------------

## 2. 为什么标准输入通常连接到终端？

### 2.1 不是 `cin` 自己决定的

程序启动时会获得标准输入、标准输出和标准错误等标准 I/O
通道。对于在交互式终端中启动的程序，通常是这样的：

1.  用户打开终端模拟器，例如桌面系统中的终端窗口。
2.  终端模拟器提供一个终端设备接口。
3.  Shell 在这个终端会话中运行，它的标准输入通常连接到该终端。
4.  用户在 Shell 提示符下输入 `./a`。
5.  如果没有指定重定向，Shell 启动的新程序通常继承 Shell 的标准输入。
6.  因而，新程序的标准输入仍然连接到终端。

所以程序执行 `cin` 时，就能接收到用户在终端中输入的内容。

### 2.2 键盘输入如何到达程序？

可以把交互式终端中的数据路径简化为：

``` text
用户敲击键盘
    |
    v
终端模拟器
    |
    v
终端设备接口
    |
    v
终端输入通道
    |
    v
程序的标准输入（fd 0）
    |
    v
C++ cin
```

这里的终端不一定是物理键盘和显示器。现代桌面环境中的终端窗口通常由终端模拟器提供终端设备接口。

在常见的终端默认设置下，终端通常以规范模式（Canonical
Mode）处理输入：用户输入的字符通常会先由终端驱动缓冲，按 Enter
后再作为一行交给程序。这是终端输入处理方式，不代表 `cin` 只能按行读取。

### 2.3 "标准输入默认是终端"并非任何情况下都成立

更准确地说：

-   在交互式终端中直接运行程序，标准输入通常来自终端。
-   使用 `<` 重定向时，标准输入来自指定文件。
-   使用管道时，标准输入来自管道。
-   程序由
    IDE、服务管理器、脚本或其他程序启动时，标准输入由启动环境决定，也可能没有可交互的终端。

因此，标准输入的来源取决于程序启动时的环境和启动方式，不是 `cin`
固定规定的。

## 3. Shell 是怎样完成 `./a < t.txt` 的？

假设有程序：

``` cpp
#include <iostream>
using namespace std;

int main() {
    int a, b;
    cin >> a >> b;
    cout << a + b << '\n';
    return 0;
}
```

文件 `t.txt` 内容为：

``` text
1 2
```

执行：

``` bash
./a < t.txt
```

Shell 会在启动 `a` 之前完成输入重定向。下面以 POSIX/Linux Shell
的典型实现方式说明。

### 3.1 第一步：Shell 解析命令

Shell 读到：

``` bash
./a < t.txt
```

它知道：

-   `./a` 是要执行的程序。
-   `< t.txt` 是输入重定向语法。
-   新程序的标准输入应该来自 `t.txt`。

`<` 是 Shell 语法，不是传给 C++ 程序的参数，也不是 C++ 代码的一部分。

### 3.2 第二步：Shell 打开文件

Shell 通常会调用类似下面的系统调用：

``` c
int fd = open("t.txt", O_RDONLY);
```

`open()` 成功后，内核返回一个文件描述符，例如 `3`。

为什么经常是 `3`？

因为一个普通进程通常已经占用了：

-   `0`：标准输入
-   `1`：标准输出
-   `2`：标准错误

因此，下一个可用的文件描述符经常是 `3`。但 `3`
只是常见示例，不是固定保证。

此时可以想象：

``` text
fd 0 -> 原来的终端输入
fd 1 -> 终端输出
fd 2 -> 终端错误输出
fd 3 -> t.txt
```

### 3.3 第三步：使用 dup2() 把文件接到标准输入

Shell 接下来会进行类似操作：

``` c
dup2(fd, 0);
```

假设 `fd` 是 `3`，那么就是：

``` c
dup2(3, 0);
```

它的效果是：让文件描述符 `0` 也指向原来由 `fd 3`
指向的同一个打开文件描述（open file description）。

如果目标描述符 `0` 原本已经打开，`dup2()` 会先关闭它，再让 `0`
指向源描述符所指向的打开文件描述。

因此，原来连接终端的标准输入被替换了。

操作之后可以理解为：

``` text
fd 0 -> t.txt
fd 1 -> 终端输出
fd 2 -> 终端错误输出
fd 3 -> t.txt
```

这里 `fd 0` 和 `fd 3`
指向同一个打开文件描述，因此共享文件偏移量等打开文件状态。

这一步是整个输入重定向的关键：

**Shell 没有修改 C++ 的 `cin`，而是改变了新程序的文件描述符
0，让标准输入从终端改为文件。**

### 3.4 第四步：关闭多余的文件描述符

完成复制后，Shell 通常会关闭原来的 `fd 3`：

``` c
close(fd);
```

此时：

``` text
fd 0 -> t.txt
fd 1 -> 终端输出
fd 2 -> 终端错误输出
```

文件仍然可以通过 `fd 0` 读取。关闭 `fd 3` 不会关闭 `fd 0`
所引用的打开文件描述。

### 3.5 第五步：使用 exec() 启动目标程序

完成重定向后，Shell 会通过 `exec` 家族的函数启动 `./a`，例如：

``` c
execve("./a", argv, envp);
```

`exec` 会用目标程序替换当前进程的程序映像，但通常会保留没有设置
`FD_CLOEXEC` 标志的文件描述符。

因此，重定向好的文件描述符 `0` 会保留下来，成为新程序的标准输入。

注意：实际 Shell 可能通过 `fork()` 创建子进程，在子进程中完成重定向和
`exec()`；也可能根据具体情况采用其他实现优化。上面描述的是典型的进程创建路径和关键操作，不要求每个
Shell 的内部代码都逐字相同。

### 3.6 第六步：C++ 程序开始运行，cin 读取数据

新程序启动后执行：

``` cpp
cin >> a >> b;
```

C++ 标准输入流从标准输入读取数据。在常见 Linux C++
运行库实现中，标准输入最终关联到进程的标准输入通道，也就是文件描述符
`0`。

而文件描述符 `0` 已经由 Shell 设置为指向 `t.txt`。

所以 `cin` 读到的是文件内容：

``` text
1 2
```

最后输出：

``` text
3
```

完整过程：

``` text
Shell 解析 ./a < t.txt
          |
          v
      open("t.txt")
          |
          v
   得到文件描述符 fd
          |
          v
      dup2(fd, 0)
          |
          v
  文件描述符 0 改为指向 t.txt
          |
          v
       close(fd)
          |
          v
    exec 启动 ./a
          |
          v
    C++ 程序执行 cin
          |
          v
  cin 从标准输入（fd 0）读取
          |
          v
       读取 t.txt
```

## 4. 为什么 `cin` 不需要重新打开文件？

因为 `cin` 的职责是从标准输入流读取数据，而不是根据文件名打开文件。

Shell 在程序启动前就已经把标准输入安排好了。等 C++
程序开始运行时，标准输入已经指向文件。

因此，以下两种启动方式中，C++ 代码可以完全相同：

``` bash
./a
```

``` bash
./a < t.txt
```

差异只在于程序启动时标准输入的来源：

``` text
交互式终端启动：

终端 -> 标准输入（fd 0）-> cin
```

``` text
输入重定向启动：

t.txt -> 标准输入（fd 0）-> cin
```

这就是标准输入抽象的价值：程序只需要读取统一的输入接口，不必为终端、文件、管道分别编写读取逻辑。

## 5. `cin`、`stdin` 与文件描述符 0 的关系

这几个概念相关，但并不是同一个对象：

-   **文件描述符 0**：POSIX 系统中进程的标准输入文件描述符。
-   **`stdin`**：C 标准 I/O
    库提供的标准输入流对象，通常底层使用文件描述符 0。
-   **`std::cin`**：C++ 标准库提供的标准输入流对象。默认与 C 标准输入流
    `stdin` 同步。

在常见 Linux 实现中，可以把关系粗略理解为：

``` text
std::cin
   |
   | 默认与 C 标准输入同步
   v
C 标准输入 stdin
   |
   v
文件描述符 0
   |
   v
当前连接的输入来源
```

严格来说，C++ 标准规定的是 `std::cin`
与标准输入流的关系；具体运行库如何实现缓冲和底层读取属于实现细节。学习
Linux 下的常见 C++ 程序时，把 `cin`
的底层输入来源理解为标准输入文件描述符 0 是很实用的模型。

## 6. 为什么 `./a 1 2` 不能代替 `cin` 输入？

执行：

``` bash
./a 1 2
```

时：

-   `./a` 是程序。
-   `1` 和 `2` 是命令行参数。
-   它们由 `argc`、`argv` 接收。
-   这条命令没有把 `1 2` 放进标准输入。

例如：

``` cpp
#include <iostream>
using namespace std;

int main(int argc, char* argv[]) {
    cout << "argc = " << argc << '\n';

    for (int i = 0; i < argc; ++i) {
        cout << "argv[" << i << "] = " << argv[i] << '\n';
    }

    return 0;
}
```

执行：

``` bash
./a 1 2
```

程序通常会看到：

``` text
argc = 3
argv[0] = ./a
argv[1] = 1
argv[2] = 2
```

而 `cin` 读取的是标准输入，和 `argv` 是两套独立机制。

两种机制也可以同时使用：

``` bash
./a 10 20 < t.txt
```

其中 `10`、`20` 是命令行参数，`t.txt` 是标准输入的数据来源。

------------------------------------------------------------------------

## 7. 管道为什么也能让 cin 读取数据？

例如：

``` bash
echo "1 2" | ./a
```

管道 `|` 会把左侧命令的标准输出连接到右侧程序的标准输入。

数据流是：

``` text
echo "1 2"
     |
     | stdout
     v
   管道
     |
     | stdin
     v
    ./a
     |
     v
    cin
```

所以 `cin` 读到 `1 2`，程序输出 `3`。

这和文件重定向的共同点是：它们都改变了程序标准输入的来源。程序本身仍然只从标准输入读取。

------------------------------------------------------------------------

## 8. 最后总结

1.  `cin` 读取标准输入，不是专门读取键盘。
2.  交互式终端中，Shell
    的标准输入通常连接到终端；没有重定向时，新程序通常继承它。
3.  `./a < t.txt` 中，Shell 在启动程序前打开文件，并通过 `dup2()`
    把文件接到文件描述符 0。
4.  Shell 随后启动程序；重定向后的文件描述符 0 通常会保留给新程序。
5.  `cin` 从标准输入读取数据，因此自然读到文件内容，无须修改 C++ 代码。
6.  `./a 1 2` 中的 `1 2` 是命令行参数，不是标准输入。
7.  文件重定向、管道和终端输入只是标准输入的不同来源。

**一句话概括：Shell 通过 `open()` 和 `dup2()`
等操作，在程序启动前安排好文件描述符 0；程序启动后，`cin`
仍然只读取标准输入，因此它能在不修改代码的情况下，从终端、文件或管道读取数据。**
